подробное пояснение че происходит в каждом файле
1 файл -- requirements.txt:
Flask — фреймворк для создания веб-сайтов на Python. Без него пришлось бы вручную 
обрабатывать HTTP-запросы, писать веб-сервер — Flask берёт это на себя.

requests — библиотека для отправки HTTP-запросов из Python-кода 
(используется в эксплойтах — ими мы "стучимся" в сайт как будто через браузер).
Команда pip install -r requirements.txt читает этот файл и устанавливает именно эти версии библиотек.

2 файл app.py -- уязвимый файл
Flask — класс, из которого создаётся само приложение.
request — объект, через который мы получаем данные, присланные пользователем (из форм, URL и т.д.).
render_template_string — функция, которая берёт текст HTML-шаблона и подставляет в него данные (аналог "заполнить бланк").
g — специальный объект Flask для хранения данных в рамках одного запроса (используем для подключения к БД).
redirect — функция, которая говорит браузеру "перейди на другую страницу".
session — встроенный механизм Flask для запоминания "кто вошёл в систему" между запросами (через куки браузера).
sqlite3 — встроенный в Python модуль для работы с базой данных SQLite (это просто файл .db на диске, не требует отдельного сервера БД).
os — для работы с путями к файлам и проверки их существования.

app = Flask(__name__) — создаёт объект приложения. __name__ просто говорит Flask, в каком файле он находится (нужно для поиска ресурсов).
app.secret_key — секретный ключ, которым Flask подписывает куки сессии (session), чтобы пользователь не мог сам себе подделать "я вошёл как admin". В реальном проекте это должна быть длинная случайная строка, здесь — учебная заглушка.
DB_PATH — вычисляет полный путь к файлу базы данных: "папка, где лежит этот скрипт" + mininotes.db
ф-я get_db() -- это функция "дай мне подключение к базе". g живёт только в рамках одного HTTP-запроса.
Если подключения ещё нет — создаём (sqlite3.connect), если уже есть — просто возвращаем его же, чтобы не открывать соединение с БД по нескольку раз за один запрос.

@app.teardown_appcontext — это "декоратор": он говорит Flask "вызови эту функцию автоматически
после каждого запроса, что бы ни произошло". Задача функции — аккуратно закрыть соединение с БД,
чтобы не оставалось "висящих" подключений.

init_db() -- это функция "создать базу данных с нуля". Построчно:

Если файл базы уже существует (с прошлого запуска) — удаляем, чтобы начать "чисто".
Открываем новое подключение.
CREATE TABLE users (...) — создаёт таблицу пользователей с колонками: id (номер, растёт автоматически), username (текст, должен быть уникальным), password (текст).
CREATE TABLE notes (...) — таблица заметок: id, author (кто написал), text (текст заметки).
Два INSERT INTO users ... — добавляют двух тестовых пользователей: admin и alice, с паролями прямо в коде (в реальном проекте так делать нельзя, пароли надо хранить хешированными — но здесь это не предмет задания).
conn.commit() — "сохранить" изменения на диск (без commit они не запишутся).
conn.close() — закрыть это временное подключение (оно отдельное от get_db(), используется только при старте).

LOGIN_PAGE = "..." Это обычная строка с HTML-кодом формы входа. 
{% if error %}...{% endif %} и {{ error }} — это синтаксис Jinja2 (шаблонизатора Flask):
когда render_template_string обрабатывает эту строку, он заменяет {{ error }} на реальное значение 
переменной error, а {% if %} — это условие "показывать эту строку только если error не пустой".

@app.route("/") — говорит Flask: "когда кто-то открывает адрес / (главную страницу), вызови
эту функцию". Функция просто перенаправляет на /login.

methods=["GET", "POST"] — эта страница принимает два типа запросов: GET (просто открыть страницу) и POST (отправить форму).
if request.method == "POST": — если это не просто открытие страницы, а именно отправка формы (нажали "Войти")...
request.form.get("username", "") — берёт значение поля username из отправленной формы.
Второй аргумент "" — что вернуть, если поля вдруг нет (пустую строку вместо ошибки).

Это и есть SQL Injection. query собирается склейкой (+) обычных строк Python прямо с тем, 
что ввёл пользователь. db.execute(query) отправляет этот текст в базу данных 
как команду. cur.fetchone() — "забери первую найденную строку результата" (или None, если ничего не нашлось).
Проблема в том, что username и password вставляются как есть, без всякой 
проверки — пользователь полностью контролирует итоговый текст SQL-запроса.

if row: — если запрос что-то нашёл в базе (значит логин/пароль подошли)...
session["user"] = row[0] — запоминаем в сессии имя вошедшего пользователя.
redirect("/notes") — перенаправляем на страницу заметок.
Если не нашёл — выставляем текст ошибки.
render_template_string(LOGIN_PAGE, error=error) — в конце (если не было редиректа)
показываем страницу входа, подставив в неё error.

Если в сессии нет записи “user” (то есть никто не вошёл) — выкидываем обратно на страницу 
входа. Простая защита "эту страницу можно смотреть только залогиненным".

Если пользователь отправил форму добавления заметки — берём текст и вставляем в базу.
здесь запрос уже правильный, с ? вместо прямой вставки текста (это называется параметризованный 
запрос — безопасный способ). Но это не спасает от XSS, потому что проблема не в том, 
как сохраняются данные, а в том, как они потом выводятся на странице.

Забираем все заметки из базы (fetchall() — все строки результата, не одну) и передаём 
их в шаблон NOTES_PAGE для отображения. Вот тут и срабатывает |safe из шаблона — текст 
заметки вставляется в HTML без экранирования, и если в нём был <script>, браузер его выполнит.
